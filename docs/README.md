# 文件索引

這個目錄把「產品感」拆成可分享、可討論、可落地使用的 Markdown 文件。建議分享給團隊時，先讓大家讀 `overview.md`，再依角色閱讀對應文件。

## 文件與用途

| 文件 | 適合對象 | 內容說明 |
|---|---|---|
| [`overview.md`](overview.md) | 全員 | 建立產品感的共同定義，說明四個核心判斷與 AI 時代的重要性 |
| [`for-engineers.md`](for-engineers.md) | 開發、Tech Lead | 說明工程師如何把使用者價值、技術成本、維護風險放在一起判斷 |
| [`for-pm.md`](for-pm.md) | PM、PO | 說明 PM 如何定義問題、排序需求、收斂 MVP、設定驗證方式 |
| [`decision-framework.md`](decision-framework.md) | PM、開發、主管 | 提供需求評審和 roadmap 排序可用的五軸判斷框架 |
| [`templates.md`](templates.md) | 實際寫文件的人 | 可複製的需求釐清、MVP、tech design、上線檢討與會議紀錄模板 |
| [`workshop.md`](workshop.md) | 分享者、主管 | 60 分鐘分享和 90 分鐘工作坊設計，含練習題 |
| [`glossary.md`](glossary.md) | 全員 | 統一產品感、MVP、真需求、成功指標等常用詞 |
| [`referer.md`](referer.md) | 維護者 | 原始參考稿，保留初始觀點和素材 |

## 建議導入方式

1. 先用 `overview.md` 做一次 30 到 60 分鐘分享。
2. 在下一次需求評審使用 `decision-framework.md`。
3. 讓 PRD 或 tech design 試套 `templates.md` 裡的欄位。
4. 一到兩週後回頭檢查：哪些欄位有幫助，哪些需要改成團隊自己的語言。

## 維護原則

- 新增文件時，先確認它是給哪個角色或哪個流程使用。
- 文件應該幫助決策，不只是堆概念。
- 如果團隊已有 PRD 或 tech design 模板，優先把這裡的欄位合併進既有流程。
- 真實案例比抽象原則更容易被採用，後續可補 `examples/` 目錄收集案例。
