# 內部分享與工作坊

## 目標

讓開發與 PM 對「產品感」有共同語言，並能把它用在需求評審、MVP 定義、tech design 和上線後驗證。

## 適合對象

- 開發工程師。
- PM / PO。
- Tech Lead / EM。
- 設計、QA、營運、客服等會參與需求討論的角色。

## 60 分鐘版本

| 時間 | 內容 |
|---|---|
| 0-10 分鐘 | 產品感是什麼，AI 時代為什麼更重要 |
| 10-20 分鐘 | 產品感四個判斷：該不該做、先做什麼、做到什麼程度、怎麼做舒服 |
| 20-35 分鐘 | 工程師與 PM 的角色差異 |
| 35-50 分鐘 | 用真實需求套 decision framework |
| 50-60 分鐘 | 討論如何放進團隊流程 |

## 90 分鐘工作坊版本

| 時間 | 內容 |
|---|---|
| 0-15 分鐘 | 共同概念與案例 |
| 15-30 分鐘 | 分組挑一個真實需求 |
| 30-45 分鐘 | 用五軸框架評估需求 |
| 45-60 分鐘 | 定義 MVP 與不做範圍 |
| 60-75 分鐘 | 工程師補充成本、風險與替代方案 |
| 75-90 分鐘 | 各組分享決策與 next step |

## 練習題

### 練習 1：需求背後的問題

題目：

> 客戶希望後台可以匯出所有欄位，並支援自訂欄位順序。

討論：

- 客戶真正要完成什麼工作？
- 現在的痛點是找不到資料、整理太慢，還是格式不符合？
- 所有欄位都需要嗎？
- 有沒有更小版本可以先滿足主要情境？

### 練習 2：MVP 收斂

題目：

> 使用者希望新增通知中心，所有重要事件都能通知。

討論：

- 哪些事件真的重要？
- 第一版要通知誰？
- 通知是即時、每日摘要，還是只在特定流程出現？
- 哪些通知如果做太多，反而會變成干擾？

### 練習 3：工程成本轉產品決策

題目：

> PM 希望所有歷史資料都能套用新的分類規則。

討論：

- 只套新資料是否能先驗證？
- 歷史資料重算的成本和風險是什麼？
- 是否需要回滾？
- 如果只支援最近 90 天，價值是否足夠？

## 分享前準備

- 選 1 到 2 個團隊最近真的遇到的需求。
- 先準備需求背景、使用者情境與目前爭議。
- 不要只講抽象概念，讓參與者實際做一次判斷。

## 分享後落地

建議把以下內容放進既有流程：

- PRD 加入「問題、範圍、不做、成功標準」。
- Tech design 加入「使用者可見行為、取捨、上線觀察」。
- 需求評審固定使用五軸框架。
- 上線後至少做一次簡短結果檢查。
