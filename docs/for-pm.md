# 給 PM 的產品感

## PM 的核心價值

PM 的價值不是收需求、排會議或寫 PRD，而是把模糊問題變清楚，並帶團隊做出值得投入的產品決策。

AI 讓交付速度變快後，PM 更不能只做需求轉交。PM 要像產品判斷中樞，把使用者、業務、工程成本和驗證方式放在一起看。

## 從需求轉交到問題定義

使用者說「我想要一個功能」時，PM 要先還原問題。

| 使用者說 | PM 要釐清 |
|---|---|
| 我需要匯出報表 | 他要完成什麼工作？現在卡在哪？多久發生一次？ |
| 這個流程很難用 | 難在哪一步？是找不到、看不懂、太慢，還是怕出錯？ |
| 希望可以自訂設定 | 是真的需要彈性，還是現有預設不符合主要情境？ |
| 要和競品一樣 | 競品解的是什麼問題？我們的使用者是否有同樣情境？ |

## PM 要判斷的五件事

| 判斷 | 問題 |
|---|---|
| 價值 | 這件事會提升收入、留存、轉換、效率，還是降低風險？ |
| 範圍 | 多少使用者受影響？是高頻、低頻，還是高價值少數？ |
| 成本 | 工程、設計、營運、客服和維護成本是多少？ |
| 時機 | 現在做是否比其他事情更值得？ |
| 驗證 | 做完後怎麼知道有效？ |

## MVP 不是縮水版需求

MVP 是最小可驗證版本。它的目的不是把功能做少，而是用最小成本驗證最重要的假設。

好的 MVP 會清楚定義：

- 這版要驗證的假設。
- 主要使用者和主流程。
- 這版不支援的情境。
- 成功標準。
- 如果失敗，下一步要調整什麼。

## PRD 應該包含的產品判斷

一份有產品感的 PRD，至少要回答：

- 背景：為什麼現在要處理？
- 問題：使用者或業務遇到什麼具體問題？
- 目標：這次要改善什麼結果？
- 範圍：這版做什麼、不做什麼？
- 優先級：為什麼它比其他事情更值得？
- 成功指標：上線後看什麼？
- 風險：體驗、技術、營運、法務或資料風險在哪？

## PM 與工程師的協作方式

好的需求討論，不是 PM 丟規格、工程估時間，而是一起收斂方案。

PM 應該主動問工程師：

- 哪些部分成本最高？
- 哪些部分風險最大？
- 有沒有更小的版本可以驗證？
- 哪些 edge case 會讓複雜度大幅增加？
- 如果先不做某個情境，使用者會受到什麼影響？

## PM 的日常檢查清單

需求進 roadmap 前：

- 我能說清楚背後問題，不只是描述功能。
- 我知道它影響哪些使用者，以及影響多大。
- 我知道不做的代價。
- 我知道它和其他需求相比為什麼更優先。

進開發前：

- 主流程、例外流程和不做範圍已對齊。
- 成功標準已定義。
- 工程成本與替代方案已討論。

上線後：

- 有看數據或回饋，不只確認功能存在。
- 有針對結果決定繼續、調整或停止。
