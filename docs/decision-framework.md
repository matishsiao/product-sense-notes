# 產品感決策框架

## 使用時機

這份框架適合用在需求評審、roadmap 排序、PRD review、tech design 前置討論，以及上線後檢討。

目標是把討論從「誰覺得重要」變成「這件事的價值、成本、風險和驗證方式是什麼」。

## 五軸判斷

| 軸線 | 核心問題 | 判斷重點 |
|---|---|---|
| Problem | 問題是否真實 | 使用者、頻率、痛點、損失 |
| Value | 價值是否足夠 | 收入、留存、轉換、效率、風險降低 |
| Cost | 成本是否合理 | 開發、設計、測試、營運、維護 |
| Experience | 體驗是否變好 | 更快、更清楚、更安心、更少錯誤 |
| Timing | 現在是否該做 | 依賴、機會窗口、替代方案、優先級 |

## 快速評分表

每項用 1 到 5 分評估。分數不是為了精準，而是為了逼出討論。

| 項目 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 問題明確度 | 只有感覺或單一抱怨 | 有案例但範圍不清 | 問題、場景、影響對象清楚 |
| 使用者影響 | 少數低頻 | 中等頻率或特定角色重要 | 高頻或高價值使用者強痛點 |
| 業務價值 | 難以連到結果 | 間接改善效率或體驗 | 明確影響收入、留存、轉換或風險 |
| 實作成本 | 大量架構變更 | 中等開發與測試 | 小成本可交付 |
| 風險 | 影響核心流程或資料 | 有可控風險 | 低風險、可回滾 |
| 驗證方式 | 無法判斷效果 | 可用回饋或局部數據觀察 | 指標、log、成功標準明確 |

建議結論不是單看總分，而是看組合：

- 高價值、高成本：拆 MVP 或分階段。
- 高價值、低成本：優先做。
- 低價值、低成本：除非能明顯改善體驗，否則不要塞滿排程。
- 低價值、高成本：拒絕或延後。
- 價值不確定：先做研究、prototype、log 或人工驗證。

## MVP 收斂問題

定義版本時，依序問：

- 哪個使用者場景最重要？
- 這版只要驗證哪一個假設？
- 80% 的常見情境是什麼？
- 哪些 edge case 可以先不做？
- 如果先不做某個情境，是否有人工或營運 workaround？
- 這版成功後，下一版自然會做什麼？

## 需求評審會議問題

會前：

- 需求背景是否足夠？
- 是否有具體案例、數據或使用者回饋？
- 是否列出不做範圍？

會中：

- 這是問題、解法，還是老闆或客戶指定的功能？
- 有沒有更小的驗證方式？
- 工程成本最高的地方在哪？
- 使用者體驗最容易出錯的地方在哪？
- 成功標準是否能被觀察？

會後：

- 決策理由是否記錄？
- 本版範圍是否明確？
- 未決問題是否有 owner 和期限？
