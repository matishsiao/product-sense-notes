# 給工程師的產品感

## 工程師為什麼需要產品感

AI 讓工程師的產出速度變快，工程師也更常直接參與原型、需求討論與方案選擇。未來有價值的工程師，不只是把需求做完，而是能幫團隊判斷「這樣做是否值得、是否可維護、是否能更小成本驗證」。

工程師的產品感，可以理解成：

> 使用者價值 × 技術成本 × 長期維護風險的判斷力。

## 工程師該多問的一層

收到需求時，不要只問「什麼時候要」。先問：

- 這個需求真正要解決的是什麼問題？
- 使用者真的會這樣操作嗎？
- 這個流程是不是可以更短？
- 有沒有更小的版本可以先驗證？
- 這會不會導致架構、資料或相容性負擔？
- 如果要支援所有 edge case，成本是否值得？

## 技術成本要變成產品語言

工程師最大的優勢，是知道實作成本和系統風險。重點不是只說「很難」或「要很久」，而是把成本翻譯成可決策的選項。

| 不夠好的說法 | 更有產品感的說法 |
|---|---|
| 這個很難做 | 完整版會動到資料模型和相容性，約 2 週；如果先支援新資料，2 天可驗證 |
| 這樣不合理 | 使用者目標是快速完成設定，我建議先把流程縮成 2 步 |
| PM 規格沒寫清楚 | 這裡有 3 個情境會影響實作，我們先決定主流程和例外處理 |
| 之後再重構 | 如果現在照這樣做，下一次加同類需求會重複改 4 個地方 |

## 工程師可以主動提出的替代方案

| 情境 | 可提出的替代方案 |
|---|---|
| 完整需求太大 | 先做 MVP，只支援最高頻場景 |
| 後台設定成本高 | 第一版先用 config 或內部工具控制 |
| 需求價值不確定 | 先做 prototype、log、A/B 或人工流程驗證 |
| edge case 很多 | 先定義不支援範圍，避免把特例做成主流程 |
| 會造成長期負債 | 提供短期方案和長期方案的成本差異 |

## Tech Design 裡應補上的產品感

技術設計不只寫架構，也要寫決策背景：

- 目標使用者與主流程。
- 這版明確要解的問題。
- 本版不處理的情境。
- 使用者可見的錯誤處理。
- 上線後要觀察的指標或 log。
- 技術債的接受原因與後續清理條件。

## 工程師的日常檢查清單

開發前：

- 我知道這個功能要解的真問題。
- 我知道主流程和非主流程。
- 我知道哪些情境這一版不做。
- 我有提出成本更低的版本，如果它存在。

開發中：

- 錯誤訊息能讓使用者知道下一步。
- 預設值、空狀態和 loading 狀態不會讓人困惑。
- 技術實作沒有把少數特例變成永久複雜度。

上線後：

- 有 log 或指標能看出功能是否被使用。
- 有辦法追蹤錯誤率、完成率或主要行為。
- 如果結果不好，知道下一步要調整什麼。
